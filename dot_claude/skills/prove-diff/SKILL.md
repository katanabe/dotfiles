# prove-diff

PR を出す前 (または Draft を ready にする前) に、差分を自己検査する。

## 何のためのスキルか

このリポジトリのレビュワーは、指摘のたびに**手元で実測**している。「このテストは変異を当てても緑のまま通る」「PR 本文の主張は実態と食い違う」「同じ形が他に N 箇所ある」。だから指摘が強く、後から直すと差分が伸びる。

このスキルは、その実測を**自分で先にやる**。観点を読んで判断するのではなく、**実行して確かめる**。

**既存スキルとの棲み分け**:
- `/review-all` (frontend-test-review / backend-test-review 等) = 技法でテストケースの不足を挙げる層
- **本スキル** = 挙がったテストが**本当に変異を捕まえるか実測する**層 + 本文の裏取り + 横展開の棚卸し

`/review-all` の後に走らせる。順番を逆にすると、実効性のないテストを増やしてから実測することになる。

## 前提

- **時間予算は全体で既定 20 分** (目安の内訳: フェーズ1 に 5 分 / フェーズ2 に 12 分 / フェーズ3 に 3 分)。超えたらフェーズ2を打ち切り、未検査の変異を明記して報告する (打ち切りは失敗ではない)
- 変異の巻き戻しは **`cp` で退避したファイルを戻す**。`git checkout` は同じ差分にある追加テストまで消す
- 変異は**1つずつ**当てる。複数同時だと、どの変異がどのテストに捕まったか分からなくなる
- **この手順で決まらず自分の判断で埋めた箇所は、成果物末尾に「裁量で埋めた点」として1行ずつ残す**。judgment を消すために規定を増やし続けると手順が仕様書になるので、余地は残したまま可視化する側に寄せている。溜まったものが次にこのスキルを直すときの材料になる

## 手順

入力は現ブランチの差分か PR 番号。**どちらで入ったかで、数える分母と出力名が決まる**。

| 入力 | 変異の分母 | 出力名 |
|---|---|---|
| 現ブランチの差分 | そのブランチの差分に現れた spec | ブランチ名 |
| PR 番号 | **その PR の差分に現れた** spec (現在の working tree ではなく) | その PR の headRefName |

PR 番号で入ったとき、working tree が PR 後の master まで進んでいることがある。その乖離自体を成果物の冒頭に1行書く。

そのうえで、**フェーズ1 の grep は作業ツリーではなく PR の ref に対して打つ**。ツリーに無いファイルを grep して、0 件を「存在しない」と読むのが最頻の誤り。

```bash
git fetch origin $(gh pr view <PR番号> --json headRefName -q .headRefName)
SHA=$(git rev-parse FETCH_HEAD)
git grep -n 'IOS_BUNDLE_ID' $SHA -- app/   # ツリーを汚さずに PR の中身を数える
```

変異実測 (フェーズ2) はファイルの実体が要るので、そこに進むときだけ checkout するか worktree を切る。

まず差分を把握する。

```bash
# base: 既定は origin/master。PR 番号が与えられた場合はその PR の base を使う
BASE=origin/master
BASE=origin/$(gh pr view <PR番号> --json baseRefName -q .baseRefName)   # PR 指定時

git diff --stat $BASE...HEAD && git diff $BASE...HEAD   # ブランチ差分
gh pr diff <PR番号>                                     # PR 指定時
```

### フェーズ1: 静的 (数分)

grep で終わる検査から先に潰す。ここで見つかるものは修正コストが最も低い。

**1-0. 分母の点呼**

差分ファイルを全件並べ、それぞれが以降のどの検査で見られるかを1行ずつ割り当てる。**分類は排他ではない** — 1 ファイルが複数に当たるなら全部書く。排他なのは「分母外」の判定だけ。

| 差分ファイル | 見る場所 |
|---|---|
| spec / `_test.rb` (追加・変更) | フェーズ2 の変異対象 |
| spec / `_test.rb` (削除・`it` の削除を含む) | **1-f** (削除した契約の後継) |
| 実装コード | フェーズ2 (対応する spec 経由) |
| PR 本文に記載あり | フェーズ3 の裏取り対象 |
| どれにも入らない | **ここで見る (下記)** |

判定に迷ったら **「そのファイルの意図を壊す変異で、赤くなるテストが存在するか」** で切る。存在しないものが分母外。

- **巻き添えは数えない**。barrel の `export` を消すと mock 経由で spec が落ちるが、それはその 1 行を守るテストではない → 分母外に置いて「間接的に守られている」と併記する
- **同種ファイル群は、値を読んでいる 1 本だけが分母内**。どれが読まれているかは spec 側から引く (`grep -rn '<キー名>' --include='*.spec.*'`)

**どこにも入らなかったファイルは、それを消費している側を grep で数える。** 設定・CI・env・lint 設定の類はテストも本文も持たないことが多く、放っておくとどのフェーズの分母にも入らないまま1度も検査されずに出ていく。

```bash
# 共有キーに1行足したなら、そのキーの参照を数える
grep -rn 'outputs.frontend' .github/workflows/   # → 6 job が参照している
```

数えた結果に対しては 1-a と同じく、全部引き受けるか、引き受ける理由を PR 本文に書くかを決める。

**1-a. 横展開の棚卸し**

差分で直した/追加したパターンを grep して、**同じ形が他に何箇所あるか数える**。数を数えずに「6箇所」と思って書くと、レビュワーが「type 単位では 20 箇所」と数えてくる。

数えた結果に対して、次のどちらかを必ず決める:
- この PR で全部直す
- 直さない理由と follow-up 予定を **PR 本文に書く** (「なぜ1本だけ残っているのか」が本文だけで追えるようにする)

**1-b. 前例に揃っているか**

新しく書いたテスト/実装と同じ役割のものを、**同ディレクトリか同 feature から1本読む**。書き方が違っていたら、違える理由があるか自問する。理由がなければ揃える。

指摘として来やすいのは: テストの render 方法 (`composeStories` 経由かどうか)、`window.location` の差し替え手順、positive control の有無、非同期の締め方 (`waitFor`)。

**1-c. 命名と判定対象の一致**

新設した型・関数・定数の名前が、**実際に読んでいる値**と一致しているか。「名前が広く読めると、後から名前どおりに直す変更が入り込む」。参照が少ない今が改名コスト最小。

**1-d. ガードが空く「窓」**

この PR とスタック次段の間で、**無防備になる期間**ができていないか。依存宣言を足すと lint ガードが外れる、集約 job の `needs` 欠落でマージゲートに穴、`FOO=$(cmd)` が fail-fast を飲み込む — いずれもこの形。

**1-e. 対の点呼 — 片側だけ書かれていないか**

フェーズ2 の変異は**有るコードしか壊せない**。書かれなかった行には当てる変異が存在しないので、ここで数える。差分で片側を書いたら、**対になる側を grep して数える。0 本なら疑う**。

| 対 | 数えるもの | 実例 |
|---|---|---|
| set / reset | 書き込み経路と、初期値に戻す経路 | `setSetupFailure` が set 1 / null 復帰 0 → 2回目以降が発火しない |
| 定義 / 呼び出し | 用意した `clear*` を、想定経路 (logout 等) から呼んでいる箇所 | `clearRegisteredPasskeyUser` の呼び出しが `packages/` 配下 0 件 |
| 成功 / 失敗 | 成功時に assert しているものを、失敗系でも見ているか | 成功時は 2 フラグ、422 系は `valid_password?` だけ |
| FE / BE | 同じ規則を両側で実装したとき、境界値が一致するか | `String.length` は UTF-16 単位・Ruby は文字数 → 絵文字で FE 活性・BE 422 |
| 新規 / 既存 | 追加したテストが、既存テストの真部分集合になっていないか | 追加 3 件が master の 13 件に含まれていた |

```bash
grep -n 'setSetupFailure' packages/client/mms/routes/app.mms_staff.tsx
# → set 1箇所 / null に戻す 0箇所
```

**隣の対称形が最短の手がかり**。同じ関数に `passkeyGate.clearFailure()` があるのに `setSetupFailure(null)` が無い — 片側だけ経路がある形は grep の並びで見える。

state の復帰経路が無いときは、同値 bail-out (`useState`) と effect deps の両方で塞がることがあるので、「再レンダーは起きるか」「deps は変わるか」を別々に見る。

**1-f. 削除した契約の後継 — 消したテストが守っていたものは誰が守るか**

フェーズ2 の分母は**追加した**テストなので、削除が主体の差分では分母が最小になり、変異は全部「新テストが守る経路」に当たって全部赤くなる。それで網に見える。実例: 削除 51 `it` / 追加 6 `it` の PR で変異 5 本が全部赤 → レビュワーの MUST 4 件はすべて**削除側の契約に後継が無い**ものだった (`configurationError` を黙る側に足しても赤くならない、`autoStarted` ref を外しても緑、ログアウト直後の再入経路)。

```bash
gh pr diff <PR番号> | grep -E '^-\s*(it|test|it\.each)\('     # 削除した it を全件並べる
gh pr diff <PR番号> | grep -E '^\+\s*(it|test|it\.each)\('    # 追加した it (後継候補)
```

削除 `it` を **1 件ずつ** 次の 3 択に割り当てる (上のコマンドの出力 1 行 = 1 件。`it.each` も 1 件)。まとめて「移植した」と書かない。**後継の探索範囲は head 全体** — この PR で追加した it に限らず、差分外に元から居る it も後継に数える。

| 割り当て | 意味 | 行き先 |
|---|---|---|
| 後継あり: `<新テスト名>` | 同じ契約 (同じ入力で同じ観測) を新テストが守っている | フェーズ2 でその新テストに、**旧 it の入力**で変異を当てる |
| 契約ごと廃止 (`<理由>`) | 守るべき挙動そのものが差分で消えた | 理由が PR 本文だけで追えるか (フェーズ3) |
| 後継なし | 挙動は残っているのに守り手だけ消えた | **🔴 候補**。フェーズ2 の変異対象に足す |

- 削除 `it` に添えてあったコメントは契約の本文として一緒に読む。`// 端末の登録済みフラグは残る。抑止しないと直後の起動でセッションを復元してしまう` のような**経路の注意書きは、その it を消すと本文からも消える**
- 「契約ごと廃止」と書くときは、その契約が **押した場合 / 自動の場合** のように前提つきで成り立っていなかったかを疑う。ボタン前提で真だった主張 (「導線が見えているだけでは誰も入れない」) を自動起動に持ち込むのがこの形
- 3 択は **「旧 it の入力を新テストにそのまま流したら、同じ観測ができるか」** の一問で決める。流せる = 後継あり / 流せず挙動も消えた = 契約ごと廃止 / 流せず挙動は残る = 後継なし。**ラベルは増やさない** (「部分後継」「入力差あり」は後継なしに置き、旧入力を注記に書く)
  - 旧 it が `configurationError` を入力し、新 it が `cancelled` しか入力しない → 種別違いで流せない → 後継なし
  - 押下起点の旧 it が自動起点の新 it に置き換わった → 押下入力は流せない → 後継なし (注記: 自動起点では同じ観測を新 it が持つ)
- 削除 `it` が 0 件なら「0 件」と記録して終わる。数えなかったのと数えて 0 だったのは別

### フェーズ2: 変異実測 (時間予算の主対象)

差分で**追加/変更したテストが守るはずの実装**に変異を当て、**赤くなるテストが1本以上あるか**を確かめる。緑のまま通ったら、そのテストは網になっていない。

**最低到達点**: 差分で追加/変更した spec / `_test.rb` **1本につき最低1変異**、**かつ 1-f で「後継なし」になった削除 `it` 1 件につき 1 変異** (旧 it が守っていた入力で当て、生存を実測して 🔴 の根拠にする。「後継あり」も入力が旧 it と完全一致でないものは同じ扱い)。
テストを1本も追加していない差分 (リファクタ・削除・掃除が主のもの) では 0 件で満たされてしまうので、その場合は **PR 本文の「変更内容」「影響範囲」の箇条書き1件につき1変異**に読み替える。差分側の行数やメソッド数で数えると粒度が恣意的になるので、数える単位は本文側の構造に紐づける。担保の主張そのものが検査対象。

**1周目が全緑だったら、2周目で消費者まで辿る**。対象ファイルだけを回して全緑でも、それは探索範囲が足りていないだけかもしれない。変異した値・メソッドの **消費者を grep で列挙し、その消費者のテストまで回して、なお全緑なら「生存」**。1周目を狭く回すのは再現を速くするため、2周目で広げるのは探索を担保するため — 幅ではなく回数で分ける。テスト0本の差分では、この2周目が唯一の網になる。
時間予算はこの工程の上限を決めるもので、下限を免除しない。予算内に下限へ届かなければ、届かなかった分を ⏭ に列挙する。

**実行系がそもそも無いとき** (コンテナ停止・依存未インストール) は、下限を「当てる対象 / 変異内容 / 赤くなるはずのテスト名」を書くところまでに読み替えて満たしたものとし、⏭ に理由を書く。可否は**対照 (下記の手順 0) を 1 本流した結果で決める**。サービスが Up に見えてもテストが動かないことがあるので、起動状態は原因の切り分けにだけ使う。

**手順は対照から始める**。変異前が緑であることを確かめないと、赤くなった原因を変異に帰属できない。テストコマンドは**リポジトリの CLAUDE.md から引く**。以下のコマンドは grow_learn (Vitest + Minitest) の例で、他のリポではそのリポのランナーに置き換える。

```bash
# 0. 対照 — 変異前に対象テストが緑であることを確認する。
#    ここが赤なら変異検査は成り立たない。BE で赤いときはまず依存サービスの不足を見る
#    (例: grow_learn では rustfs が落ちていると S3 経路のテストが NetworkingError で赤くなる)
yarn workspace client test run --retry=0 path/to/impl.spec.ts

# 1. 退避 (git checkout は同じ差分の追加テストまで消すので使わない)
cp path/to/impl.ts /tmp/prove-diff-backup

# 2. 変異を1つ当てる (Edit で1箇所だけ)

# 3. テスト実行 (1周目) — 対象ファイルだけに絞り、失敗したテスト名まで取り出す
yarn workspace client test run --retry=0 path/to/impl.spec.ts 2>&1 | grep -E '×|Tests '
yarn workspace mms test run --retry=0 path/to/x.spec.ts 2>&1 | grep -E '×|Tests '
docker compose exec -T rails bundle exec rails test path/to/x_test.rb 2>&1 | grep -A4 -E 'Failure|Error'  # -A4 が無いとテスト名は次行なので落ちる

# 4. 戻す (次の変異へ行く前に必ず)
cp /tmp/prove-diff-backup path/to/impl.ts
```

記録するのは、対照が緑だったこと・当てた変異・**赤くなったテストのファイル名とテスト名**。「N 件 green のまま」だけでは、後から読んで何が守られていたか分からない。

狙う変異の型 (生存しやすい順):

| 型 | 変異の作り方 |
|---|---|
| ガード節を消す | `if (!x) return` / 早期 return を落とす |
| prop・引数を落とす | `loading={loading}` を消す、`{ useFallback: true }` → `false` |
| 定数を取り違える | キー定数 A を キー定数 B の値に置き換える (同じ値を書く2定数は特に危険) |
| 連結を削る | `pathname + search + hash` → `pathname` のみ |
| 判定を緩める | 分類の分岐を 1 ケースだけ通る形に緩める |
| 配線を切る | 環境変数由来の定数を `''` に置き換える |
| トリガの射程を広げる | 「起動時だけ」のつもりの条件から限定子を落とす (`!loading && !currentUser` → `!currentUser`)。level 条件になっていると稼働中の失効でも走る |
| 削除で成立した契約を壊す | 掃除・削除が主の差分向け。削除したコードを戻しても呼び出しが無く挙動差が出ないなら、**削除によって初めて成立した契約の側**を壊す (旧実装形に書き戻す) |

**変異が生存したら、まずテストデータの判別力を疑う**。実装ではなく入力が弱いことが多い:

- **同時達成**: 1つの入力で複数のフラグが同時に立つと、ラベルや対応を入れ違えても通る → フラグが割れる入力を足す
- **境界未踏**: 閾値から離れた値だと、閾値が緩められても通る → 境界の1つ手前を踏む値にする
- **負例が1件だけ**: 分類の負例が1つだと、判定が緩んでも通る → 別系統の負例を足す
- **positive control 不在**: 失敗系だけだと「常に失敗する壊れ方」も緑 → 成功する1件を足す
- **観測手段が無効**: テスト環境が代入を無視する / 部分一致が広いセレクタも拾う / 修正前後で同じ値になる → 観測方法そのものを変える (setter を spy、完全一致、CSSOM から引く)
- **テスト名と経路のずれ**: 早期 return で目的の経路に到達していない → stub をパラメータ化して名前どおりの経路を通す

### フェーズ3: 本文の裏取り

PR 本文とコード内コメントから、**事実主張だけを抜き出して列挙する**。「〜のため」「〜なので」「実測した」「〜になる」の形をしている文。抽出単位は**本文の 1 行** (箇条書き 1 項目 / 表の 1 行)。数値表は行ごとに 1 主張として数える。そのうえで **実測コマンドを 1 つ書けないものは対象外**にし (将来予定・見積もり・スクショ)、対象外にした行だけを列挙する。落としたものが見えれば件数の恣意性は消える。

列挙した1つずつを**実測コマンドで確認**する。裏が取れないものは:
- 直せるなら直す
- 直せないなら**本文から落とす** (根拠のない主張を残す方が高くつく)

**主張の語が 2 通りに読めたら、両方の読みで測る**。「総 diff N 行」は additions とも additions+deletions とも読める。片方の読みでしか成立しないなら、直す対象は数字ではなく**本文の語**。

特に食い違いやすいのは: テスト環境の挙動についての断定、「リスク判断が必要」と書いた項目が実はデッドコード削除だった、性能上の根拠 (実測すると桁が違う)、コメントが参照していない定数を根拠にしている。

## 出力

`tmp/prove-diff/<branch>.md` に書く。ブランチ名の `/` は `-` に置換する (`feat/123-x` → `feat-123-x.md`)。`tmp/` が gitignore されていないリポでは、先に ignore するか別の ignore 済みディレクトリを使う (`git check-ignore -q tmp/ || echo 未ignore`)。

```markdown
# prove-diff: <branch>
検査時刻 / base / 差分 N files (うち分母外 M files)

## 📋 フェーズ1 の記録 (指摘が出なくても全項目残す)
- 1-0 分母: <path> → 見た検査。分母外は消費者の実測件数まで
- 1-a 横展開: <パターン> → 他 N 箇所
- 1-b 前例: 読んだ 1 本 → 揃っている / 違える理由
- 1-c 命名: <名前> → 実際に読んでいる値
- 1-d 窓: 空く期間の有無
- 1-e 対: <set / reset など> → 片側 N 件 / 対側 M 件
- 1-f 後継: 削除 N it → 後継あり A / 廃止 B / 後継なし C (C は 🔴 に転記)

## 🔴 要修正
- [観点] 何が / どう確かめたか (コマンドと結果) / どう直すか

## 🟡 検討
- [観点] 何が / 判断材料 / 直さない場合に本文へ書くこと

## ✅ 確認済
- 当てた変異と、赤くなったテスト

## ⏭ 未検査
- 未検査のまま残した変異と、その理由 (時間予算 / 実行環境が無い / 依存待ち)

## 裁量で埋めた点
- 手順が決めていなくて自分で決めたこと (次にこのスキルを直すときの材料)
```

**フェーズ1 は何も見つからなくても全項目残す**。「数えた結果 0 件だった」こと自体が成果物で、指摘が出なかった工程を書かない形にすると、検査した事実が消える。

区分の物差し:

- **🔴** = マージ後に挙動が壊れる。**依存の着地で自動的に露出するものを含む** — 「引き金がまだ無いから今は発火しない」を理由に 🟡 へ落とさない。自分の差分が原因で、後続が着地した瞬間に壊れるなら 🔴
- **🟡** = 放置しても挙動は変わらない (本文の不整合・命名・将来の壊れやすさ・横展開の残り)
- **変異が生存したテストの穴は 🔴**。実装が今日正しくても、次の変更で無音で壊れる。1-f の「後継なし」とフェーズ2 の生存はここに入る (「挙動は変わらない」を理由に 🟡 へ落とさない)

他人の PR をレビューするときは「未配信なら今の問題ではない」が正しいが、**自己検査では逆**。塞いでいるのが自分の後続 PR なら、それは猶予であって免除ではない。

区分は**重大度の分類**であって、後続アクションとは別。既定の後続アクションは「🔴 は修正まで進める / 🟡 は提示だけして判断を仰ぐ」だが、**呼び出し時に「検査だけ」と指示された場合はそれが優先**で、🔴 も提示に留める (ready 化前の下見はこの使い方になる)。
